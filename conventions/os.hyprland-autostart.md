# Convention: Hyprland autostart (os.hyprland-autostart)

The Hyprland `exec-once` list is a security-critical boot chain. Its first
user-visible command MUST be `keystone-startup-lock`, which launches the lock
screen and kills the session if the lock surface fails to appear. Dropping or
reordering this entry exposes an unlocked desktop after reboot — a fail-open
security defect.

This convention originated in ks.systems/os when the `exec-once` list was
generated by Nix: a priority collision between `mkDefault` (priority 1000) and
`mkAfter` (priority 100) silently replaced the entire base exec-once list,
dropping the lock screen, D-Bus setup, polkit agent, and clipboard manager.
The list now lives in the dotfile template (`templates/hyprland/.config/hypr/
hyprland.conf`) and in each user's stowed copy — the failure mode changed
shape, but the invariant did not.

## Boot chain context

```
greetd (auto-login) → UWSM → Hyprland → exec-once → keystone-startup-lock → hyprlock
```

If `keystone-startup-lock` is missing from `exec-once`, or if hyprlock fails
to present a lock surface, the script terminates the session rather than
exposing an unlocked desktop. This is a fail-closed design. See
`modules/home/scripts/keystone-startup-lock.sh`.

## Base list ownership

1. The base `exec-once` list is owned by the template `hyprland.conf`
   (`templates/hyprland/.config/hypr/hyprland.conf`) and, once seeded, by the
   user's own dotfiles copy. Nix does not generate it.
2. The base list MUST contain `keystone-startup-lock`, appearing after
   environment plumbing (`systemctl --user import-environment`,
   `dbus-update-activation-environment`) and before all other user-visible
   entries.
3. The `template-startup-lock` check (`tests/default.nix`) enforces this
   ordering at build time for the template. It is the successor of the old
   Nix-module assertion — do not weaken it.
4. Users who edit their seeded `hyprland.conf` MUST keep
   `keystone-startup-lock` first among user-visible entries. Personal
   additions belong in `user.conf` / `host.conf`, which are sourced at the end
   of the file and therefore cannot displace the lock entry.

## Adding autostart commands

5. Session-start-critical commands belong in the template's `exec-once` block,
   after `keystone-startup-lock`.
6. Personal or per-host autostart entries belong in `user.conf` or
   `host.conf` (`exec-once=` lines) — never spliced above the lock entry in
   `hyprland.conf`.
7. Nix modules MUST NOT contribute `exec-once` entries via
   `wayland.windowManager.hyprland.settings` — that settings tree is not
   rendered anywhere; the stowed dotfiles are the only live config. Anything a
   module needs at session start must ship in the template (and be called out
   in the seed contract) or run as a `systemd.user` service bound to
   `graphical-session.target`.

## Customizing the lock command

8. Users MAY replace `keystone-startup-lock` in their seeded copy with a
   different lock command by editing the `exec-once` line in their dotfiles —
   there is no Nix option for it; the seeded `hyprland.conf` is the single
   source of truth.
9. Any replacement command MUST implement fail-closed semantics: present a
   lock surface or terminate the session.
